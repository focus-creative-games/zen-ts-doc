# 能力与取舍

本页评价 ZenTS 自身设计，不是其他项目版本的功能清单。对外部方案的具体能力与性能应按其对应版本另行验证。

## CLR 互操作

按需绑定和签名桥复用减少业务 Wrap 维护，Attribute/AOT XML 明确配置 Alias、MarshalAs 和扩展方法。短名冻结与全签名懒解析提供稳定入口；声明门面避免仅因实际对象类型不同而泄漏更多成员。

成本在于：需要完整定义数值、泛型、byref、装箱、结构体和重载规则，并跨后端验证。无逐类型 Wrap 不意味着无 Generate、无裁剪配置或任意泛型运行时代码生成。

## 引擎与平台

原生 V8 通过自己的引擎接口隔离，使用官方原始源码静态构建；WebGL/微信复用平台 VM，与原生共享 CLR 内核。这能避免小游戏重复嵌入解释器，也把平台模块、GC 和 wasm ABI 的差异限定在适配层。

代价是 V8 SDK 编译与分发、iOS JITless，以及 HostJs 能力最低要求。微信转换 SDK 的实际输出也需要独立验收，不能以浏览器成功推断所有小游戏平台支持。

## 工程和工具

只读 UPM、Library SDK 和自动生成插件 meta 适合 Git 包安装；TS emit/声明与 Inspector 使源码和调试流程统一。Editor 调试服务不进入 Player，也不等于平台远程调试都已实现。

## 应如何比较

优先比较：关键 CLR 特性是否有对照测试；新增类型需维护多少配置；发布后 AOT/裁剪是否可靠；GC/Reset 是否泄漏；Editor 调试和 SDK 分发是否符合团队流程。性能、包体和内存应在相同应用测量，当前正确性记录不构成排名。

先读[项目状态](../getting-started/project-status.md)了解证据与限制，再用自己的目标设备和工作负载评估。

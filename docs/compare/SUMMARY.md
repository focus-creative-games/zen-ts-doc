# 选型思路

选择脚本方案需要比较自己的工作流和平台约束，不能只看引擎名称或测试函数数量。ZenTS 的特点是沿用 ZLua 的 CLR 设计、按需绑定、共享签名桥，以及 Native V8/HostJs 双后端。

## 评估维度

| 维度 | ZenTS 的设计与成本 |
|---|---|
| 绑定维护 | 不要求业务逐类型 Wrap 白名单，但仍需 AOT 与裁剪保留 |
| 一致性 | Mono/IL2CPP 和 V8/HostJs 采用同一 CLR 语义 |
| 开发体验 | TS 声明、检查、Source Map、Editor Inspector |
| 原生引擎 | 官方 V8 静态 SDK；需维护多平台工具链与缓存 |
| Web 平台 | 使用平台 VM，无重复引擎；受宿主能力和预编译模块约束 |
| 安装分发 | 兼容只读 Git package，SDK/插件归项目本地 |
| 验证成熟度 | 以具体平台记录为准；现有模拟器/工具结果不替代真机 |

## 与现有方案比较

比较 Puerts、Lua 或自建 V8 方案时，应用相同的业务样本、平台、裁剪级别、预热条件和发布体积口径。ZenTS 的结构性取舍可从代码确认；不能据此推断其他项目的当前功能缺失，也不能没有基准就声称性能更高。

对于已有成熟绑定或工具链的项目，迁移成本也应计入。先复现关键调用、泛型、生命周期和小游戏打包，再决定是否迁移。详见[能力分析](FEATURES.md)和[验收矩阵](../getting-started/compatibility.md)。

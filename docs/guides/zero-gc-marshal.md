# 分配与数据传递

ZenTS 通过共享签名桥、绑定计划缓存和显式值策略减少跨语言调用成本。是否产生 GC 分配取决于具体类型、方向、引擎和调用形态，不能承诺所有调用零分配。

## 先减少跨边界次数

优先批量传输并缓存 `GetFunction` 委托、类型对象和常用 closure。不要每帧查找模块导出或在细粒度循环里反复切换 JS/CLR。首次绑定和首次泛型闭合的成本应与稳定态分开测量。

## 选择正确形态

| 形态 | 应考虑的成本 |
|---|---|
| CLR wrapper | 保留 CLR 身份，包含对象/GC 根管理 |
| ByVal struct | 值复制；含引用字段需要安全写回 |
| JS Array / Table | 按成员转换，可能创建数组或对象 |
| Bytes / to_bytes | 明确复制，不能假设零拷贝 |
| Opaque | 调用期借用，不能跨 await 或长期缓存 |
| out 元组 | 创建 JS 结果数组，嵌套结果不展平 |

WASM 内存增长后旧 TypedArray view 可能失效；引擎适配层刷新内部视图，不代表业务可以长期持有任意内存地址。

## 测量方法

在实际目标平台以 Unity Profiler 和对应 JS 工具测量稳定态分配、CPU、峰值内存以及长时间 GC。区分 Editor Mono 与 Player IL2CPP、V8 与平台 VM，并记录脚本输入、批量大小和预热条件。当前验收记录是正确性证据，不是公开性能排名。

ABI、复制和写回规则优先于局部“零 GC”优化。任何优化都不能改变选中的重载、声明门面或值类型语义。
